# Investigation of the v2 development disagreements

This review examines the eight disagreements and one failed case from the [development run](DOCUMENT_SUPPORT_V2_RUN.md). It uses the saved judge decisions, the current cached PubMed titles and abstracts, and the original MedAESQA reference records and excerpts. It makes no API calls and does not change labels, predictions, or scores. These observations are working interpretations, not independently adjudicated gold labels.

The reference relation is a dataset annotation attached to a sentence/citation record, often accompanied by a particular evidence excerpt. The v2 judge sees the complete current title and abstract and decides whether at least one relevant assertion is supported. A reference of `neutral` maps to false in our binary calculation. These tasks and evidence scopes can differ; a mismatch alone does not establish which decision is correct.

The separate human review marked question 126 / PMID 33484483 as supported, whereas the judge and its neutral reference agreed on no support. That case is **not one of the eight reference disagreements**; it shows that agreement with a reference does not by itself establish a correct judgment. The reviewer accepted technical wording such as aneuploidy as equivalent; the judge required a more explicit definition. Question 146 / PMID 34132818 was also in the human review.

## Failed case: question 138 / PMID 15236629

The sentence identifies Sudafed and Afrin ingredients. The abstract explicitly connects an oral dose of pseudoephedrine with the Sudafed product name, but does not discuss Afrin or oxymetazoline. The two original records are labeled neutral. Under the v2 partial-support task, this is potentially a useful case: one part has textual evidence while another is absent.

Both live attempts ended in `ValueError`. The runner retained the error class, case ID and elapsed time, but not the response or a detailed validation reason. Therefore we cannot determine whether the problem was an invalid quote, schema consistency, parsing, incomplete output, or another `ValueError`. Do not count this as a false prediction or infer the cause from the case text. Improving future diagnostics to store a safe, structured error category without secrets or raw service errors would make a later retry more informative.

## What to do next

Update: the [v3 development prompt and safe failure categories](DOCUMENT_SUPPORT_V2.md) have been implemented and checked locally. The remaining steps below still require a new versioned development experiment and independent held-out assessment; no new score has been produced by this change.

1. **Clarify the task before tuning:** distinguish support for a cited component from complete coverage of the sentence. Decide what counts as an acceptable direct inference or technical-to-plain-language equivalent, while preserving population, causal direction, uncertainty, and treatment combinations. A related topic or mere study aim is not enough.
2. **Improve evidence checks:** ensure the quoted evidence supports the exact proposition being credited, not merely a related background statement. Test examples such as the adolescent psychotherapy pilot and the NSAID list. Exact substring matching alone cannot enforce semantic support.
3. **Make failures diagnosable:** record safe validation categories, retain attempt history, and test the failure paths locally before spending more API calls. The original failed outputs cannot be reconstructed.
4. **Use a new, versioned development experiment** for any prompt or schema change. Keep this run and its 17/25 agreement and 0.31 kappa intact. Report the same cases, failures, abstentions, and reference disagreements; do not replace dataset labels to manufacture agreement.
5. After development, freeze the method and use a separately prepared held-out set. The held-out cases remain untouched; this investigation does not demonstrate that targets are met or that the live ADK Verifier is calibrated.
